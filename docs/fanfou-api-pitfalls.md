# 饭否 API 踩坑记录

写给要从零实现一个饭否客户端的人。官方 API 文档（wiki）只覆盖了理想情况，这份记录只写**文档没写、但一定会踩到**的行为，全部来自实测（2026 年，基址 https://api.fanfou.com ，OAuth 1.0a）。

---

## 0. 环境与基础

- Base URL：https://api.fanfou.com
- 列表接口普遍支持 mode=lite ，返回精简字段，省流量。
- **必须带浏览器 User-Agent**。饭否的 CDN 与部分接口在网关层按 UA 过滤，用 URLSession 默认 UA 可能拿到 403 或空响应。客户端统一伪装成桌面 Safari 的 UA。
- 图片域名（s3-img.meituan.net）与 fanfou.com 需要 ATS 例外；API 本身走 https 没问题，但 status 里的 url 字段常是 http://fanfou.com/... 。
- 时间戳格式是 RFC 822 风格：Fri Jul 17 23:47:04 +0000 2026 。**日期是单数字、且可能出现连续两个空格**，解析前要把 "  " 归一成 " "（iOS 的 en_US_POSIX DateFormatter 对 "EEE MMM d HH:mm:ss Z yyyy" 能解，但双空格会失败）。
- 所有时间字段是 **UTC**；饭否用户心智与「历史上的今天」都按 **北京时间（UTC+8）** 计算，跨日必须用北京时区，否则日期会错一天。

## 1. OAuth 1.0a

- **签名基串里的 URL 必须用 http://**（即使实际请求走 https）。把 scheme 强制替换成 http 再算 HMAC-SHA1，否则签名不匹配。这是饭否最著名的坑。
- 基串 = METHOD & pctEncode(scheme://host/path) & pctEncode(排序且编码后的参数串)。
- 参与签名的参数 = oauth_* + query + 表单参数；**只有 application/x-www-form-urlencoded 的表单才计入**，multipart 上传不计入。
- 参数先各自百分号编码，再按「编码后的 key、再编码后的 value」排序后拼接。
- 百分号编码按 RFC 5849：空格 %20、加号 %2B、保留字符全部编码。**注意别用会把非 ASCII 字母放过的字符集**（比如 Foundation 的 CharacterSet.alphanumerics 会放过中文），否则中文参数不编码、签名必错。
- 解析 access_token 响应（x-www-form-urlencoded）时，先把 + 还原成空格，再做百分号解码。
- oauth_timestamp 用秒级 Unix 时间；oauth_nonce 每次随机（16 字节十六进制即可）。

## 2. ID 与游标：id / rawid / since_id / max_id

这是最容易出错的一块。

- `id` 是加密字符串（如 QofB7iACzoQ），`rawid` 是对应的数字（如 276063573）。
- **rawid 单调递增、可用于排序/水位线，但游标参数要的是 id 字符串。**
- `since_id`：返回**严格新于**该 id 的内容（排除边界）。
- `max_id`：返回更旧的内容；**不接受数字 rawid**，传 rawid 会被静默忽略（照原样返回第一页）。
- 最坑的是：**不是所有接口都支持 max_id**（见收藏一节），而且参数错了不会报错，只是不生效。

实测：以下三种写法返回完全相同的一页
    max_id=213062756      （rawid，数字）
    max_id=2gjtw6jsnvk    （id 字符串）
    （不传）
说明该接口忽略了 max_id。

## 3. 分页

- 普通时间线（statuses/home_timeline、user_timeline、mentions …）用 page 做 offset 翻页是有效的；max_id 则更精确。
- **收藏（/favorites）完全不支持 max_id，只能用 page。**
- **收藏分页的坑最集中**，实测特征（以某账号为例）：
  - 每页条数不固定：count=60 时返回 56/49/56/57/60/60/60/22，并非 count。
  - 相邻页**会重叠**（有 1~3 条重复）。
  - 页序稳定但**不是按 rawid 排**，而是按「收藏时间」；同一页里 rawid 可以跨越十几年。
  - 因此：**绝不能按 rawid 重排**，客户端必须原样保持服务端顺序；去重后再展示。
  - 末页很小（可能只有 2 条），再下一页返回空数组（用空数组判断到底，不要用「条数 < count」）。
  - 网页版显示 23 页（约 460 条），API 实际只有 417 条唯一记录——**计数与可拉取条数不一致**（已删除/失效的条目仍计入计数）。
- **列表里会出现畸形条目**：我们实测到某页第 25 条长这样：

    { "id": false, ... }

  用整体数组解码（如 Swift 的 [Status]）会让**整页解码失败**，表现为「翻到某一页就再也翻不动」。必须**逐条容错解码**（失败的元素丢弃），这是我们收藏翻页卡死的真正原因。

## 4. 图片

### 4.1 图片 URL 是 CDN 变换，不是原图

status 的 photo 对象：
    thumburl   .../zf_359286.jpg@120w_120h_1l.jpg    120x120
    imageurl   .../zf_359286.jpg@200w_200h_1l.jpg    200x200
    largeurl   .../zf_359286.jpg@596w_1l.jpg         596 宽

- largeurl 只有 596px 宽，直接拿来做全屏大图会糊。
- **去掉 @ 后缀（保留到 .jpg）就是原图**：实测同一张图 2048x1423 / 1.1MB，而 @596w 只有 135KB。
- 结论：列表用小图（省流量），看大图时用去掉变换后缀的原始 URL。

### 4.2 上传

- /photos/upload.json 用 multipart/form-data，文件字段名 photo。
- **multipart 请求不要把表单字段算进 OAuth 签名**（表单参数与 query 一起入签名是 application/x-www-form-urlencoded 的规则）。
- 服务端对格式/体积挑剔：**统一转成 JPEG** 最稳。iPhone 直接产出的 HEIC / Live Photo 静帧 / 宽色域图容易失败。
- 客户端应先降采样再上传（我们取最长边 2048、JPEG、上限约 3MB，并在超标时逐步降质量）。
- 大图降采样要用 ImageIO 的缩略图（CGImageSourceCreateThumbnailAtIndex），**不要先把原图整体解码**：6000 万像素的图直接解到内存会把分享扩展/App 干掉（实测崩溃）。

## 5. 发帖后的「审核」

- /statuses/update.json 与 /photos/upload.json 返回 200 且带完整 status，**但帖子可能进入人工审核**，此时：
  - 它**不会出现在** home_timeline / user_timeline 里；
  - 没有任何接口能查询审核状态，也没有回调。
- 客户端必须自己兜底：发帖成功后**乐观插入自己的时间线**并标「审核中」；过一段时间（我们用 30 分钟）仍没在服务端时间线出现，就当作未通过，把内容（含图片）放回草稿箱。
- 判定「通过」的办法就是：后续刷新时服务端时间线里出现了这条 id。

---

## 6. 转发

- 转发帖的 text 里**可能已经内联了原文**，形如：
    我的评论 转@作者 原文……
    点赞 RT@作者 原文……
  同时又提供 repost_status（原帖对象）。
- 如果客户端无条件地把 repost_status 再拼一次，就会出现「原文展示两次」。
- 正确做法：text 中已含 转@ / 转 @ / RT@ / RT @ ，或已包含原文文本时，直接原样显示；否则才拼 转@作者 原文。
- 发转发用 repost_status_id 字段。

---

## 7. 消息：@我、私信、关注请求

- /statuses/mentions.json ：默认 count 约 20；count=40 会在同一序列上多返回一倍，两者前 20 条一致（说明是稳定序列）。
- 私信会话列表 /direct_messages/conversation_list.json ：返回的是「会话 + 最后一条 DM」，按最后消息时间倒序；用它推进未读水位线时用最后一条 DM 的时间戳。
- 受保护账号的关注：/friendships/create.json 返回成功但对方时间线上不会立刻 following，需要关注请求流程（accept/deny 接口）。
- 未读水位线建议用 rawid（@我）与时间戳（私信）分别记录，客户端本地维护。

---

## 8. 限流与调度

- 历史上账号级限额约 **1500 次/小时**。
- 客户端应做令牌桶 + 优先级：交互请求（用户主动触发）优先；后台索引/回填请求让位，并且**不要在用户前台操作时抢带宽**。
- 参数错误、被忽略的参数都不会体现在限流里，别指望靠报错发现调用问题。

---

## 9. 错误处理

- 出错时通常返回 JSON 错误体；但注意：
  - **参数被忽略时返回 200 + 正常数据**（最危险，容易误以为成功）；
  - 网络层可能返回空 body / 非 JSON；
  - 解码失败与请求失败要分开处理（前者往往是数据畸形，应该跳过而不是整页失败）。

---

## 10. 客户端落地的检查清单

- [ ] OAuth 签名基串用 http://，UA 用浏览器。
- [ ] 非 ASCII 的 OAuth 参数值做 UTF-8 百分号编码。
- [ ] 时间解析容忍单数字日与双空格；跨日按 UTC+8。
- [ ] 列表按 id 去重；时间线按 rawid 归并排序；**收藏保持服务端顺序**。
- [ ] 所有列表用**逐条容错**解码，畸形条目跳过。
- [ ] 收藏只用 page 翻页，空数组才算到底。
- [ ] 大图用去掉 CDN 变换后缀的原图。
- [ ] 上传前统一转 JPEG 并降采样（ImageIO 缩略图，避免整图解码）。
- [ ] 发帖后乐观插入 + 审核标记 + 超时转草稿。
- [ ] 转发文案去重（转@/RT@/已含原文）。

## 反模式：不要再用 `/search/users`

- `GET /search/users.json?q=...` 已经**停用**：它返回 **HTTP 200 + 空 body**（不是 404）。
  把空 body 交给 JSONDecoder 会得到「data was corrupted」（Cocoa error 3840），
  所以任何仍然调用它的客户端都必须在解码层把「空 200」视为「无结果」。
- 用户搜索**没有替代接口**：
  - `/search/public_timeline.json` 搜到的是**提到**这个名字的帖子，作者几乎不是本人；
  - `users/show` 只接受登录名 / 用户 id；
  - `users/show` 的 `?name=`、`?q=` 参数被**静默忽略**（任何值都返回调用者自己）；
  - 状态 payload 里没有 `entities` / `user_mentions`。
- 结论：客户端只保留**本地已索引用户**的匹配，不要再接这个接口。

## 昵称（@提及）无法反查用户

状态正文里的 `@xxx` 存的是**昵称（display name）**，不是登录名，而且昵称并不唯一。
实测这些路径都无法把昵称解析成用户：

| 尝试 | 结果 |
| --- | --- |
| `users/show.json?id=<昵称>` | 404 |
| `users/show.json?screen_name=<昵称>` | 404 |
| `users/show.json?name=<昵称>` / `?q=<昵称>` | 200，但**忽略参数**，返回调用者自己 |
| `/search/users.json?q=<昵称>` | 200 + 空 body |
| `/search/public_timeline.json?q=<昵称>` 的作者 | 只有讨论过 TA 的人，没有本人 |
| 我的好友 / 粉丝列表（各翻 8 页 × 100） | 未包含 |
| 发帖人的好友列表（前 200 位） | 部分命中 |

能**确定**拿到 id 的只有：

1. `user.id` —— 作者本人；
2. `repost_user_id` + `repost_screen_name` —— 转发目标（注意：`repost_user` 这个对象**不存在**，
   只有这两个扁平字段，很多客户端会漏解）；
3. 本地索引里已经见过的用户（优先匹配唯一的登录名 `screen_name`）。

推论：**绝不要用「搜索结果第一条的作者」来猜昵称指向谁** —— 那正是「点 @A 跳到恰好讨论过 A 的 B」的成因。

## 教训：不要把「解释页」当成答案

客户端点不开昵称时，给出「没找到这个人」是正确的（宁可无跳转，也不要跳错人），
但要清楚这是**API 能力边界**：搜索一次并不能让昵称变得可解析（实测索引不会因此增长）。
